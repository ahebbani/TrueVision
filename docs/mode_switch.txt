There are really three separate pieces of state in this project, and that is why the behavior is a little subtle.

First, the ESP32 has its own local mode state. In truevision_main.ino, the active firmware mode is stored in s_mode, and that is what the ESP32 audio task obeys. The audio transmit task checks s_mode directly in truevision_main.ino: if s_mode is FACE, it stops streaming audio; otherwise it keeps reading I2S and sending packets. So on the ESP32 side, mode directly controls whether audio is physically transmitted.

Second, the ESP32 derives that mode from either the hardware switch or a Pi override. The normal path is the mode switch on GPIO 35 and 36. In setup, the firmware reads the switch once at boot and stores the initial mode in truevision_main.ino. After boot, the supervisor task polls the switch every 50 ms and updates the switch-selected mode in truevision_main.ino. The decode rule is:

1. A high, B low means AUDIO.
2. A low, B high means FACE.
3. Matching levels are treated as invalid, and the firmware keeps the last valid mode.

That invalid-state behavior matters because the switch is not treated as “three-position.” In production, the switch is really expected to select one of two valid single modes. If the pins match because of a wiring fault or a transient mid-transition state, the ESP32 does not deliberately switch into BOTH; it holds the last good mode.

Third, the Pi has its own requested mode and its own effective mode. That logic is in main.py and main.py. The Pi keeps the last mode packet it heard from the ESP32 in current_mode, but it does not blindly obey BOTH anymore. The helper in main.py does this:

1. If the requested mode is AUDIO, the effective mode is AUDIO.
2. If the requested mode is FACE, the effective mode is FACE.
3. If the requested mode is BOTH, the effective mode is BOTH only when the server is available.
4. Otherwise, BOTH falls back to the last known single mode.
5. On cold Pi startup, that fallback defaults to FACE.

So the system no longer has a single global “mode” variable. The ESP32 has one notion of mode for audio transmission, and the Pi has a separate effective mode for whether it should run face recognition, local audio, or both.

The Pi updates its requested mode only when it receives a mode packet from the ESP32. That happens in the serial receiver callback path in main.py. The ESP32 sends those mode packets in a few cases:

1. When its effective mode changes, via set_mode in truevision_main.ino.
2. Once at boot, via announce_mode in truevision_main.ino and truevision_main.ino.
3. When the Pi sends a force-mode or clear-mode packet, because the ESP32 recomputes its effective mode in truevision_main.ino.

The Pi can also explicitly override the ESP32. The Pi-side CLI option force-mode is parsed in main.py, and if present the Pi sends a FORCE_MODE packet to the ESP32 when the receiver starts in main.py. On the ESP32, that packet is handled in truevision_main.ino. The important detail is that this override is not permanent: it stays active only while heartbeats are still arriving. If the Pi stops heartbeating for more than 8 seconds, the ESP32 clears the override and falls back to the hardware switch in truevision_main.ino.

That leads to the startup-order story.

If the Pi starts first and the ESP32 starts later, the behavior is mostly good. The Pi receiver opens the serial port and starts sending heartbeat packets every 3 seconds in esp32_serial_audio.py. When the ESP32 boots, it reads the switch, sets s_mode, and sends one startup MODE_CHANGE packet in truevision_main.ino. Since the Pi is already listening, it should receive that and align itself.

If the ESP32 starts first and the Pi starts later, the behavior is not fully robust yet. The ESP32 sends only one startup announcement. If the Pi is not listening at that moment, that packet is just lost. When the Pi later comes up, it does start heartbeating every 3 seconds, but the ESP32 heartbeat handler in truevision_main.ino only updates s_hb_last_ms. It does not re-send the current mode. That means the Pi can miss the true switch state and remain in its own fallback effective mode until one of these happens:

1. The user flips the switch, causing a fresh MODE_CHANGE packet.
2. The user double-presses the button, causing a BOTH request packet.
3. The Pi sends a force-mode override.
4. The code is changed to make the ESP32 re-advertise mode.

This is the race you are worried about, and your instinct is correct: the current one-shot boot announcement is not sufficient to guarantee convergence when the two devices boot independently.

There is another nuance here: if you implement “advertise switch mode every so often,” you should not actually advertise the raw switch position. You should advertise the ESP32’s effective mode. That is because the Pi may have forced a temporary override, and in that case the raw switch does not describe what the ESP32 is really doing. The correct thing for the ESP32 to tell the Pi is “this is the mode I am currently obeying,” not “this is what the switch says.” In this firmware, that means advertising s_mode or the result of apply_effective_mode, not just s_switch_mode.

So your proposed design is good, but the heartbeat-triggered version is cleaner than a blind periodic timer.

The best synchronization design here would be:

1. Pi starts in a safe single local mode.
2. ESP32 still announces mode once at boot.
3. Every time the ESP32 receives PKT_HEARTBEAT, it replies with a MODE_CHANGE packet describing its current effective mode.
4. The Pi then converges to the correct mode within one heartbeat interval, even if it missed the boot packet.

That would solve the startup-order problem with almost no extra complexity, because the heartbeat path already exists. It also avoids unnecessary serial traffic compared with “advertise every few seconds forever.”

On the server side, yes, that is checked periodically, but separately from mode synchronization. The Pi constructs a ServerConnection in main.py, does one immediate check, then starts a background thread. That background thread calls check repeatedly in server_connection.py. In the current Pi entrypoint, the interval passed in is the CLI argument server-check-interval, default 30 seconds, from main.py and main.py. The main loop also re-samples server availability every same interval in main.py and re-applies the effective mode when the server comes or goes.

One subtle limitation there: ServerConnection itself can do mDNS discovery in server_connection.py, but the current main.py only creates a ServerConnection if a server URL or TRUEVISION_SERVER_URL is provided in the first place, in main.py. So in practice, the Pi is not doing blind background discovery unless you already configured the server path.

The short version is:

1. The hardware switch picks the ESP32’s normal single mode.
2. The Pi can temporarily override that mode.
3. BOTH is now treated on the Pi as a request, not a guarantee.
4. The server gate is what decides whether BOTH is actually allowed.
5. Startup synchronization is still one-shot, so the “ESP32 first, Pi later” case can still miss the true mode.
6. Your heartbeat-based re-advertisement idea is the right way to close that gap.
