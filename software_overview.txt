The software and firmware for TrueVision Smart Glasses can be divided between two processors, the Raspberry Pi and an ESP32. The ESP32 handles the real-time input and output and the user interface whilst the Raspberry Pi does most of the processing and machine learning. Together they result in the system’s facial recognition, speech transcription, and AR display while maintaining low latency and privacy.  

 

System can be divided into groups as following:  

    ESP32 (firmware) 

    It captures audio from a digital microphone via the I2S interface and stores it in a short buffer in RAM which then is sent over to the Raspberry Pi via a wired connection (UART or USB). It also handles the user's inputs such as video-only or audio-only modes and can also drive a privacy LED when it is collecting audio and video. It also does basic power monitoring through an ADC input and can implement low battery alerts to make sure the system is in optimal working condition through reset from brown-out events to prevent unstable operation. It can be connected to MOSFETs to power off both the Pi and itself if the voltage gets too low. It also handles all the user inputs from the push buttons which lets the user toggle between the Audio-only mode, Video-only mode and neither.  

    Raspberry Pi (software)  

    Runs a Linux based software application written in Python. It receives audio packets from the ESP32 and processes them through a speech to text pipeline (Whisper) and uses the transcribed output from this to be overlayed as text onto the micro-OLED Display (which is connected to the Raspberry Pi via USB or HDMI). Simultaneously, it also gets input from the Pi Camera module and uses dlib's 128-D embedding model to detect and recognize faces which it stores in a local SQLite Database. It combines the recognized faces and transcribed text composited into a visual overlay which is displayed on the micro-OLED display through an HDMI driver board. Simple message-based coordination between the two processors (Pi and ESP32) keeps the system synchronized, so audio capture, face recognition and display run simultaneously without blocking each other.  

 

At the startup (power on), the glasses default to Dual mode (having both audio transcription and video recognition) and pressing audio and video buttons can lead to Audio-only and Video-only modes which will allow the user to select their experience. The LED will also be turned on to alert others that the user is using audio transcription or facial recognition.  

 

A stretch feature that we could implement is audio-based user recognition which would allow the system to associate detected voice with a known individual. This would affect the latency of the system, which is already very sensitive in live transcription and facial recognition system. It is included in the state machine diagram to show the overall future system capability, but it will not be part of the current implementation but rather a future one.

The software ocmbines signal-processing and machine-learning algorithnms to provide real time speech trancripton, facial recognition and AR overlay generation. These are implemented both on the ESP32 and on the Pi locally to minimize latency and ensure privacy of user data.  

 

2.1 Speech Transcription  

 

Audio Capture begins on the ESP32 which samples the digital microphone through the I2S interface. The I2S peripheral streams 16-bit PCM samples into short DMA buffers which when filled triggers an interrupt. Upon this event, the firmware packages the buffered PCM samples and transmits them to the Raspberry Pi visa UART/USB connection.  

 

On the Raspberry Pi, the incoming audio frames are concatenated into short segments (approximately 1s) and processed through a lightweight version of Whisper, an encoder-decoder transformed model for automatic speech recognition [1].  

 

The encoder converts the log-Mel spectrogram into contextual embeddings. The decoder generates text tokens representing spoken words which the post-processing merges into readable sentences with timestamps. It achieves low latency operation by running Whisper in streaming mode with overlapping windows, so new words appear every few hundred milliseconds.  

 

1.2 Power Management Logic  

The ESP32 continuously samples battery voltage through its ADC and uses threshold-based logic to generate warnings or initiate shutdowns: 

    V < 3.6V: Low-battery alert sent to Pi. 

    V < 3.3V: Enter low-power mode or cut power via external MOSFETs. 

    V < 2.6V: Brown-out detector resets MCU 

This ensures stable operation and prevents flash corruption or unsafe discharge. 

 

1.3 Display and Coordinate mapping:  

Recognized faces and transcribed text are displayed on a micro-OLED display. A simple affine-transformation matrix maps the camera coordinate system to the optical display coordinates, correcting for parallax between the camera and the user’s eye [2]. The compositor synchronizes updates, so captions and face labels remain spatially aligned with the real scene. 

 

Computer vision systems  



Facial recognition (algorithm overview)

The Raspberry Pi runs a dlib-based pipeline for on-device, real-time face recognition. Frames from the Pi Camera are converted to grayscale and passed to a face detector (HOG by default; an optional CNN detector is used automatically if its model file is present) to obtain bounding boxes. A 68‑point landmark predictor is applied to each box and a 128‑D face embedding is computed with dlib’s ResNet descriptor. Identification uses nearest‑neighbor search (L2 distance; initial threshold ~0.6) against a local SQLite database.

To improve robustness to masks, angles, and lighting, the system stores multiple templates per person and learns incrementally during a session: if a face crop is sharp (variance of Laplacian above a threshold), sufficiently different from that person’s existing templates (diversity margin), and outside a short cooldown, a new template is saved. A per-person cap (e.g., 30) with pruning prevents unbounded growth. Session logic treats people as present/absent with a short absence‑grace window (~2s); last_seen_at and seen_count update only on absent→present transitions so counts don’t inflate while someone remains in frame. The overlay shows “Name (seen N)” above the box and “Last: <timestamp>” below it.

Future / Stretch Algorithm – Audio User Recognition 

An extension is speaker recognition using a pretrained ECAPA-TDNN model [3]. The model would generate 192-D speaker embeddings from short audio segments and match them to stored profiles, allowing the system to label who is speaking alongside the transcribed text. This algorithm is computationally heavier and is therefore reserved as a future enhancement.

3.1 Audio Collection: 

 

For Audio collection from the mic, the ESP32 employs the I2S protocol to collect the audio packets from the digital microphone.  

 

Figure 1: Image of the I2S protocol data packets alongside the SCK and Word select signals [4] 

 

The I2S protocol is a three-wire serial protocol with a clock, data, and “word select” line. In this case, “word select” indicates the channel, right or left, with which data currently being transmitted is associated [4]. Through the I2S protocol the ESP32 is able to select these words found by the microphone. It then continuously shifts 16-bit PCM samples (words) to memory using DMA buffering, allowing real time audio collection without blocking the processor.  

 

Once the buffer fills, the ESP32 firmware’s interrupt handler marks it as ready and transmits it to the Raspberry Pi over a wired UART/USB connection. Each transmission contains a short block of PCM samples representing a few tens of milliseconds of audio.  

 

On the Raspberry Pi, these samples are concatenated and decoded into a continuous waveform, which is then converted into a log-Mel spectrogram used as input to the Whisper speech to text model. The decoded text is temporarily stored in memory before being sent to the display compositor for overlay. After the audio is transcribed, the Raspberry Pi represents the results as short text segments tagged with timestamps. These text segments are overlaid on the video output in real time. The overlay module keeps a lightweight data structure that links each text string with its display position and timing, allowing smooth updates on the micro-OLED screen. 

 

3.2 Communication between ESP32 and Raspberry Pi  

 

For the current prototype, communication between the ESP32 and the Raspberry Pi will use a custom lightweight packet format transmitted over a wired UART interface operating at 1 Mbps. The UART protocol used in this custom communication structure below follows standard asynchronous serial communication principles outlined by Espressif Systems [5].  

 

The custom communication protocol packet looks like this: 

    Start Flag: 1 byte - fixed value, marking the beginning of a packet. 

    Packet Type: 1 byte - identifies the message category (0x01=Audio, 0x02=Button Event, 0x03=Battery Status, 0x04=Command Ack). 

    Sequence Number: 2 bytes - incremented with each packet to maintain order and detect any missing frames. 

    Payload Length: 2 bytes - number of bytes in the payload. 

    Payload Data: variable size  

    Checksum (CRC): 2 bytes - CRC-16 or XOR-based checksum for error detection. 

 

This consistent framing provides reliable real-time data transfer over UART which provides sufficient bandwidth for real-time audio teaming from ESP32 to Pi during live transcription and is more power-efficient than USB. However, it can also be reused directly over USB in future iterations which may help when having speakers in the system or larger snippets of audio which may be needed for audio recognition. In general, this structure allows the Pi to parse incoming audio blocks and control messages asynchronously without data loss or misalignment. 

 

 

Computer vision systems 

Facial recognition data structures (persistent and runtime)

The facial recognition data is persisted in a local SQLite database. The faces table stores each person’s id, name, a legacy single embedding (retained for backward compatibility and to seed the multi‑template table), created_at, last_seen_at, and seen_count. A second table, face_embeddings, holds multiple templates per person as binary embeddings along with created_at and a quality score. This multi‑template design captures pose, mask, and lighting diversity, while a per‑person cap with pruning prevents unbounded growth.

At runtime, the recognizer keeps lightweight in‑memory maps to minimize database I/O and keep per‑frame matching fast. embeddings_by_person caches the templates, keyed by person_id and loaded once per frame; meta_by_person provides the display metadata (name, seen_count, last_seen_at) for labels; presence_state tracks whether each person is currently present or absent to drive the session logic; last_detected_ts records when a person was last seen to enforce the short absence‑grace window; last_added_ts records when a template was last added to enforce the cooldown for incremental learning.

Thresholds for matching (L2), template diversity, and image quality, as well as the cap on templates per person, are tunable so deployments can balance accuracy, speed, and storage. All model and database paths are resolved relative to the script location so the application runs reliably regardless of the working directory.
